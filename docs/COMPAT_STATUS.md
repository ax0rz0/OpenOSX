# macOS compatibility: measured status

Generated by `tools/compat/coverage.py` against the corpus in
[TEST_CORPUS.md](TEST_CORPUS.md). The point of this document is that
"run macOS apps" is no longer a vibe: every number here is a finite,
named work list, and it can be regenerated on any commit.

```sh
cd tools/compat
python3 coverage.py inventory /path/to/openosx/libs... -o inventory.json
python3 coverage.py report /path/to/Some.app -i inventory.json
```

Neither tool needs macOS, otool, nm, or a running VM: they read Mach-O
directly, so coverage can be tracked from CI on Linux.

### Reading this honestly

The encouraging part is the shape of the gap, not just its size. Roughly
**86% of the app's symbol demand targets libraries OpenOSX already ships** -
libSystem and libc++ alone account for 492 of 733 - and the true holes are
concentrated in three frameworks we have never built: AppKit, CoreGraphics
and CoreVideo.

Better still, the gaps split into two very different kinds of work:

- **Incremental**: libSystem (14), Foundation (14), CoreFoundation (7),
  IOKit (3), CoreServices (2), Security (42). These are libraries we already
  build; each missing symbol is a function to implement, not a framework to
  invent. 82 symbols total.
- **Structural**: AppKit (48) and CoreGraphics (38) require the stack in
  [AQUA_UI_PLAN.md](AQUA_UI_PLAN.md). This is the multi-year work.

**And symbol coverage is the optimistic number.** The app sends **810 distinct
selectors** and subclasses **7 classes**. Implementing 48 AppKit symbols would
make it *link*; it would then die on the first unimplemented method. The
subclassed classes are the expensive ones, because subclassing requires a
compatible ivar layout rather than merely the right method names.

### The cheapest real milestone

`CC_MD5_*`, `CC_MD4_*` and `__powidf2` are missing from libSystem despite
CommonCrypto being in the tree - that smells like a linkage/re-export gap
rather than absent code, and it is the sort of thing that is fixed in an
afternoon. Chasing the 82 "incremental" symbols would take a Tier 0 CLI
binary from *nearly* running to running, which is a far nearer milestone than
the GUI work and would validate the whole loader/dyld path with a real
third-party binary.
